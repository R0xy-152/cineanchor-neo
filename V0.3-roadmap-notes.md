# V0.3 Roadmap Notes (DRAFT — captured, not scheduled)

> Status: DRAFT. Recorded per 启鸣 2026-07-03 ("先落成草案，不落实"). These are forward directions from `10-启明-requirements.md`, NOT committed loops. Language: English (planning artifact). Each item is framed deterministic-first → bounded-AI-later, so we never jump straight to the most expensive/riskiest implementation. AI admissibility governed by ADR-010 (draft).

## Origin

From 启鸣's forward requirements on the character-birthday template. Intent endorsed: push the birthday (and future) templates toward a "production standard" feel. Key reframing (see ADR-010): almost all of 启鸣's AI ideas sit in the **pre-render static-artifact layer**, which is compatible with our four hard criteria — the issue is sequencing and cost, not principle.

## Item 1 — Scene-adaptive fonts

- **Goal:** font/text presentation matches subject mood (gothic girl → blackletter; little girl → doodle/graffiti). Directly addresses the "production feel" gap.
- **Deterministic-first (near-term, recommended first step):** curate a **font library** + a **style tag** (user-selected, or a light classifier picking gothic/cute/military/elegant) → deterministic font mapping. Gets ~80% of the value, zero per-frame AI risk, fully controllable.
- **Bounded-AI-later (deferred):** AI recognizes subject → generates a single **croppable asset sheet** of needed image assets; human crops/approves. Admissible under ADR-010 (offline, static, human-reviewed) but much larger/riskier (distortion, licensing, control) → own loop + activation decision.

## Item 2 — AI-generated dialogue / lines

- **Goal:** user inputs a character bio → generate plausible lines fitting the video rhythm (~20s). Note this grows birthday from a 15s MVP to a 20s+ narrated version = **character-birthday V2, not loop 10**.
- **Deterministic-first:** user hand-enters copy (current model).
- **Bounded-AI-later:** AI drafts lines from bio, human edits before render. Low frame-risk (static text, reviewable) → admissible under ADR-010, optional/off-path first.

## Item 3 — Voiceover

- **User-upload (near-term, safe):** user uploads a voice track; add an audio-mux step (FFmpeg). No AI. Small but real new pipeline dimension (first audio in the product).
- **Bounded-AI-later:** AI voice clone (train on uploaded sample) → static generated clip. Admissible under ADR-010, deferred, separate.

## Item 4 — Three-function product shape (启鸣 2026-07-03)

启鸣 proposed V0.3 as three game-ops deliverable types, all within the ADR-001 toB positioning:

1. **生贺 (character birthday/greeting)** — input character PNG/GLB + BGM (incl. character voice) → pick template **by personality** (傲娇/腹黑/温柔…) → output. Personality-driven template selection is a natural extension of template-fill; voice as **user-upload** is the safe path (matches Item 3).
2. **枪皮 (weapon-skin showcase)** — input skin poster → **AI live2d effect** / input GLB → fixed camera template → effects driven by material/color/subject (bg, fx) → output.
3. **无人机航拍 (drone/aerial for new-map launches)** — reuse the V0.1 Blender pipeline: import game map → **record camera in browser** → export → AI polish lighting/fx.

**Andy assessment: direction endorsed** — all three are real ops launch materials (character/skin/new-map). The drone case is the strongest addition: it is the **first time the loops 07-09 deterministic camera engine surfaces as a product feature** (the moat, sold openly) rather than hidden inside a template.

**Three boundary calls to lock (governance, not画质):**

- **B1 — Drone "record camera in browser" = a deliberate positioning exception.** It exposes camera recording to the user, which conflicts with ADR-001 ("user never touches camera/FOV"). Acceptable, but must be framed as a distinct **"guided camera-capture" template** (preset + record inside a fixed map, NOT free-timeline editing), consciously — not a silent breach of "not a free editor." 启鸣 to ratify explicitly.
- **B2 — The two AI touchpoints route through ADR-010's static-artifact vs per-frame-pixel line.** Same sentence, different landing: offline static layered/background/lighting-reference artifact → allowed; a black box that redraws the customer's **hero subject** frame-by-frame (video2video over skin/map) → the thing to avoid.
- **B3 — Skin "AI live2d" is admissible only split in two:** AI **offline** slices the poster into layered static artifacts (layers / occlusion inpaint) → a **deterministic** parallax/deform engine animates them. A black-box "AI animates the poster into frames" is per-frame generation.

## Item 5 — Commercial video-AI stance (启鸣 2026-07-03, recorded verbatim as an open divergence)

**启鸣's position:** introducing a **commercial video-generation API** (Kling/Veo/Runway/Seedance-class) will **not** produce flicker/drift; those artifacts came from the unstable **local Comfy + diffusion** stack (AnimateDiff/SVD-class), not from frontier commercial models.

**Andy: concede the flicker point.** Frame-to-frame temporal consistency on frontier commercial models is largely a solved problem; "AI = flicker" is retired as an argument. BUT flicker is only **one** of the four criteria. Removing it leaves three that are **model-quality-independent**:

1. **Distortion / subject fidelity** — the ops bar is not "smooth," it is "this skin's engraving / this face / this logo text must be **pixel-faithful** to the customer asset." Even a very stable commercial model **smoothly repaints** the subject → a smooth-but-slightly-wrong skin is still a reject. Higher bar than temporal stability.
2. **Controllability** — we need *this* trajectory / *these* keyframes precisely; generative gives "a nice clip," not "this exact camera move."
3. **Reproducibility / versioning (ADR-003/005)** — a remote black-box service updates/deprecates server-side → cannot guarantee same-input→same-output or long-term re-render. This is an **architecture property, not画质** — a commercial API is *less* controllable here.

**Reframed boundary (post-concession):** the knife-edge is no longer "AI = flicker" but **"does this generative pass rewrite/repaint the customer's hero subject pixels."** Rewriting the hero subject (video2video over hero asset) = still avoid; producing only **offline static auxiliary artifacts** (layers, sky/background plates, lighting-reference images) for deterministic compositing = allowed. Higher commercial-model quality **strengthens the static-artifact path — it is not a warrant for per-frame video2video on hero assets.**

**Governance note:** this materially **reopens the premise of ADR-004** (which was written against unstable *local* diffusion). Introducing a commercial video API would be a formal decision = an **ADR-004 revision + ADR-010 admissibility-condition update**, not an incidental add. Recorded here as a live Andy/启鸣 divergence to resolve at that decision, per draft convention.
